How an edit travels
The walkthrough you give when an interviewer says “take me through a request.”
1 You type. Tiptap turns the keystroke into a small Yjs update
and the screen paints immediately, before any network call.
2 y-indexeddb stores the update in the browser, so it survives
a refresh or a dead connection.
3 The update travels over the WebSocket to whichever
gateway instance holds your connection.
4 The gateway checks your role (viewers can’t write), applies
the update to the room and publishes it on Redis.
5 Every other gateway with that room open forwards it to its
clients, where Yjs merges it deterministically.
6 Updates are appended to a log in MongoDB and periodically
compacted into a snapshot.

Key concepts
The ideas you must be able to explain on a whiteboard. Each one deserves a short section in your

CRDT or OT? The decision interviewers probe
Both let many people edit one document. They differ in who decides how edits combine.
OT (operational transformation) CRDT (what Synapse uses)
How it works A central server orders edits and transforms each one
against those it hasn’t seen.
Every edit carries IDs and metadata, so any copy can
merge edits in any order.
Central server Required to order every edit. Not required for correctness; copies converge on
their own.
Offline editing Hard: long offline sessions need complex rebasing. Natural: edits merge whenever they arrive.
Cost Simple data, complex server logic. Extra metadata in memory, so it needs compaction.
Typical fit Always-online editors with one authoritative server. Offline-first apps and multi-server sync.
Synapse uses a CRDT (Yjs) because offline editing is a core feature, not an add-on. Being able to say that sentence, and defend
it, is the point of this project.

Choices to defend
Each one is the seed of an architecture decision record (ADR). Interviewers love “why not X?”
Yjs over Automerge
Yjs has the most mature editor bindings
(ProseMirror, awareness) and very
compact updates. Automerge is a
strong alternative with a JSON-like
model; name it in your ADR.
A custom ws gateway over
Socket.IO
The Yjs sync protocol is binary and
already handles catch-up after
reconnects, so Socket.IO’s extra layers
add little. Writing it yourself is the
learning.
MongoDB over Postgres
Snapshots and update logs are binary
blobs keyed by document, and Atlas
adds search. Postgres would work
equally well; say so, and explain what
would tip the choice.

Project 1  Synapse Hard problems and proof
Hard problems and proof
Solve these yourself; they are the conversation. Then publish the numbers, each with how you

Hard problems you’ll solve
Each one is a ready-made interview story: the problem, the options, what you chose and why.
Permissions can’t live in the shared document
Approach. Keep content eventually consistent, but check roles
on the server when a client joins a room and on every incoming
update. The gateway drops writes from viewers.
Documents grow forever
Approach. Append updates to a log, merge them into a
snapshot every N updates, then trim the log. Keep named
versions as separate snapshots so history survives compaction.
Reconnecting after a long partition
Approach. Yjs exchanges state vectors on connect, so each side
sends only what the other is missing: no duplicates, no loss.
Reconnect with exponential backoff and jitter.
Scaling WebSockets past one server
Approach. Gateways are stateless. Each room subscribes to a
Redis channel, so any instance can serve any client, and
MongoDB (not a server) holds the truth.
Typing stays fast in big documents
Approach. Keep the editor out of React re-render paths, throttle
presence updates to every 50–100 ms, and measure keystroke-
to-paint with the Performance API.
Accessible live collaboration
Approach. Announce joins with a polite live region, never move
focus because of a remote edit, and make every canvas action
reachable by keyboard.
