# ADR 0017: Per-document chat

**Status:** accepted

## Context

People editing a page together want to talk without leaving it. Comments are anchored to text and are
for feedback; chat is the quick back-and-forth. The question was where chat should live in a system that
already has two consistency domains (ADR 0002).

## Decision

Chat is a **third, separate thing**: an ordinary append-only message log, not part of the shared document.

- **Transport:** the same authenticated WebSocket as the document, with two new message types
  (`MSG_CHAT` 4, `MSG_CHAT_ERROR` 5). The sign-in, the role check and the cross-gateway relay all come for free.
- **Storage:** MongoDB collection `chat_messages`, indexed on `{docId, _id}`, with a TTL index so messages
  expire (180 days, `CHAT_RETENTION_DAYS`). A message is **saved before anyone sees it**, so what was shown
  is still there after a refresh. If saving fails the sender is told ("unavailable") and nobody sees it.
- **Who may do what, decided on the server for every message:** owners, editors and commenters send;
  viewers read. The author's **name and the time come from the server** (from the signed-in account), never
  from the client, so a message cannot be sent as someone else.
- **Input handling:** plain text only. Control characters and the invisible bidirectional overrides (used to
  make text read backwards) are removed; at most 2,000 characters; empty messages are refused.
  The page shows text as text, so markup never runs.
- **Rate limit:** 5 messages in a burst, then one every 2 seconds, per person per room (not per browser tab).
- **Several gateways:** the gateway that receives a message saves it and publishes it on the bus; the other
  gateways only hand it to the people connected to them (it is saved once).
- **History:** `GET /documents/:id/chat?before=&limit=` for anyone who can read the document; the browser
  loads the newest 50 and "Load earlier messages" pages backwards. Live messages and history are merged by id.
  After a reconnect the newest page is fetched again, so a short offline gap is filled in.
- **In the page:** a "Chat" tab beside Comments and History, with an unread count on the tab. A message
  from someone else is announced politely to screen readers (own messages and old history never are), and
  focus is never moved because a message arrived.

## Evidence

`server/test/chat.test.ts` (27 tests): delivery to everyone in the room, isolation between documents,
ordering, the server-set author, roles (including a role lost mid-session), cleaning, rate limiting per
person across tabs, an unavailable store, a failing database, delivery across two gateways with a single
save, a malformed message closing only its sender, history paging and its permissions against a real
MongoDB. I broke three rules on purpose (let viewers send, drop the rate limit, skip the relay) and each
was caught. `web/src/lib/chatStore.test.ts` (16) and `Chat.test.tsx` (14) cover the browser side.
`e2e/tests/chat.spec.ts` runs nine scenarios with two real people in Chromium and WebKit (live chat,
saved history, the unread badge, typing never interrupted, read-only viewers, markup shown as text,
too-fast refusal with the text returned, offline and catching up, a stranger refused), and axe scans the
Chat tab.

## Limits and costs (read these)

- **Not private from the system.** Messages are readable by the database and operators. There is no
  encryption beyond HTTPS.
- **Everyone who can read the page can read its chat, including old messages.** Removing someone stops their
  access to all of it, but chat sent while they had access stays visible to others (and was seen by them).
- **No editing, deleting, reporting, reactions, mentions, typing indicators, per-person read receipts,
  attachments, links that click, or search.** Without delete or moderation tools, an open invite link
  (ADR 0012) means anyone holding the link can post until it is revoked.
- **A catch-up after reconnecting fetches only the newest 50.** If more than 50 messages arrived while
  someone was offline, the older part of that gap is not filled in automatically.
- **The rate limiter is in memory on each gateway**, so the same person connected through two gateways gets
  two allowances. The unread count is not saved: a refresh resets it.
- **Chat does not work offline.** Unlike document edits, a message is not queued; the box is disabled with a
  reason while disconnected. (A chat message that waits for hours would arrive out of context.)
- A person's name is saved with each message when it is sent; renaming later does not change old messages.
- Message order is by id (time plus a counter); across gateways within the same second it can differ slightly.

## Alternatives

- **Chat messages inside the Yjs document** (a shared array): works offline and needs no new storage, but
  anything that can write the document could rewrite history, viewers could not take part safely, the
  document would grow forever, and it would break the content/access split of ADR 0002.
- **REST plus polling:** simpler, but not live, and it would duplicate the sign-in and access checks.
- **A third-party chat service:** less code, but a new dependency, cost and data sharing.
