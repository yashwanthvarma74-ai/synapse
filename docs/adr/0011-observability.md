# ADR 0011: Metrics with OpenTelemetry, Prometheus and Grafana

**Status:** accepted

## Context

The brief asks for sync latency, reconnects and open sockets from the browser, gateway
and API on one dashboard. Several of the interesting failures (a lost Redis relay, a
database outage, a slow connection) are invisible to tests and to the people running the
system unless something is measuring.

## Decision

1. **Metrics, not traces or logs.** OpenTelemetry **metrics** in the server, exposed on
   `/metrics` and scraped by **Prometheus**, shown in **Grafana**, with the dashboard and
   alert rules in git (`observability/`). The dashboard is generated by a script and
   provisioned with UI edits off, so it cannot drift from the repository.
2. **The OpenTelemetry API is called everywhere, the SDK is registered only at start-up.**
   Without the SDK the calls are no-ops, so tests and any run without monitoring pay
   nothing and need no setup.
3. **The browser reports through a beacon, not the OpenTelemetry browser SDK.** A small
   batched `POST /telemetry` carries a metric name, a number and a label. The server
   accepts only an **allowlist** of names, labels and ranges and turns them into
   OpenTelemetry metrics. Browsers are untrusted, so nothing else is accepted.
4. **Latency is measured as an echo.** Each browser pings the gateway every 5 s over the
   sync socket and times the reply. It covers browser, network and gateway, uses no clock
   shared between machines, and reflects any simulated delay. It is a proxy for "how soon
   do others see my edit", not a direct measure of it.
5. **Fixed, tiny label sets, never ids.** Labels are words (`result`, `kind`, `role`,
   `reason`, `outcome`, route pattern). No user, document or URL ever reaches a metric.
   This keeps Prometheus fast and keeps metrics free of who is editing what.
6. **The availability measure is `synced / (synced + failed)`**, counting only connections
   that dropped by themselves. Cancelled attempts are excluded.
7. **Measurements stop while a tab is hidden**, because browsers throttle background timers
   and the result would describe the browser, not the connection.

## Consequences

- **Good:** one place to see user experience and server health together, and the faults from
  ADR 0010 (relay down, database down, unsaved rooms) are visible as they happen. Verified by
  breaking Redis and MongoDB while watching it.
- **Good:** negligible cost: about 1 to 3 points of CPU and 12 MB of memory at 100 editors,
  latency unchanged within noise (single runs, see OBSERVABILITY.md).
- **Cost, serious:** the browser-reported availability measure **cannot see a total outage**:
  if the server is down no browser can report it. Prometheus's own `up` alert covers it, but
  a real external probe is still needed for an honest uptime number.
- **Cost:** no traces, so a slow request cannot be followed across browser, API and gateway.
- **Cost:** a beacon means another endpoint to protect and rate limit (it is
  authenticated, validated, limited to 100 events a request and 60 requests a minute).
- **Cost:** `/metrics` has no authentication. It binds to 127.0.0.1 and must be protected
  by the network in production.
- **Cost:** the allowlist must be changed in two places (browser and server) to add a metric.

## Alternatives considered

- **OpenTelemetry browser SDK exporting OTLP:** the standard route and gives traces, but
  adds bundle weight and lets browsers send arbitrary data to a collector. The beacon is
  smaller and strictly controlled; this is the trade to revisit if traces are wanted.
- **Hosted monitoring (Datadog, Grafana Cloud):** quicker to start, but data leaves the
  machine and it does not fit a self-contained portfolio project.
- **A hand-rolled `/stats` page:** no history, no alerting, nothing to show a reviewer.
- **Measuring edit propagation directly with timestamps:** needs synchronised clocks
  between browsers and gateways. The echo avoids that.
